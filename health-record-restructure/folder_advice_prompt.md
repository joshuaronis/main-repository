# Prompt for a session that improves the Skill Updates folder

I want you to improve my skill-change notes folder, `Skill Updates`, which I'll attach as a zip. Its `README.md` opens "Skill Updates — start here": read it first and follow its process, then `Process.md` and `Long skills/Method.md`. The folder is the knowledge folder for changing my skills, and this job changes the folder itself, not any skill. Work out what you can on your own; ask me only for what only I can do. Don't read my skills beyond what the folder holds in `Skills/*/Releases/`, and don't write anything in Notion.

## Where this comes from

On 2026-10-24 a session restructured `health-record` from one `SKILL.md` of about 441,000 characters into a main file and nine reference files, following this folder. Everything below is what that job found the folder could do better. Each point says what happened, what it cost, and what I think the fix is; weigh each against the folder's own rule — no more complicated than it needs to be, and nothing kept that won't help a later change — and tell me which you took and which you set aside, with the reason. The job's working files, including its build and check scripts, are on the branch `claude/elegant-newton-yd228c` of my GitHub repository `joshuaronis/main-repository`, under `health-record-restructure/`, if you can reach it; if not, ask me for them.

## What to change

1. **The scripts and briefs assume a skill that is one text.** `number_and_split.py`, `xref_check.py`, `aggregate_findings.py`, `build_candidate.py` and `make_targeted_packs.py` each take one TEXT, and the briefs describe "the text under review" as one file cut into parts. A multi-file skill now exists (health-record), and others may follow. The job worked around it by running the scripts per file and concatenating the files for `xref_check.py`. Give the method one documented way to work on a folder of files. The cheapest that keeps every existing script unchanged: a pair of scripts, one that concatenates a skill folder into one text with a marker line before each file (say `<!-- file: references/menu.md -->`), and one that splits such a text back into the folder; then the whole pipeline — parts, findings, judges, candidate, fix check — runs on the concatenation, and the split-back is the last step before release. Say in `Method.md` that `fix_old` must never span a marker, and add the marker form to the briefs' file notes. Test the round trip on the health-record release in `Skills/health-record/Releases/` (concatenate, split back, compare byte for byte) before you rely on it.

2. **Checks a multi-file skill needs that the folder has nowhere.** The job wrote them for itself; make them general and keep them in `Long skills/Scripts/`, with a line each in `Method.md`'s table: (a) every reference file is named by its path in `SKILL.md`; (b) each file's "Sections by file" map line, or whatever the skill's own map is, is identical in every file; (c) each file's list of what it holds matches the `##`/`###` headings in it; (d) no "(*Title*, above)" or "(*Title*, below)" pointer names a title outside its own file, and every "this section" and "end of this section" is read; (e) `xref_check.py` run on the concatenation; (f) the character offset at which `SKILL.md`'s always-needed part ends, against the compaction limit (about 20,000 characters, from Claude Code's documentation of 2026-10-18). The job's `check_split.py` and `check_headers.py` on the branch do most of this against the one-file original; the general versions should need no original.

3. **The md5 listing is doubled.** `check_folder.py` requires every non-empty file's md5 of the newest release in both `About.md` and `Changelog.md`. With one file that was one line twice; with ten files it is ten md5s twice, and every later release of a multi-file skill will list ten again. Keep the changelog as the place that records every version (the README already says so) and let `About.md` carry only the release's name and the md5 of `SKILL.md`, or the zip's; change `check_folder.py` to match, and the README's table of notes.

4. **`release.py` replaces the title.** It sets `SKILL.md`'s first `# ` heading to the stamped name, so "# Health Record" becomes "# health-record-2026-10-24-0741" and the readable title is gone, while the reference files' headers still say "Health Record — §2". I decided the stamp goes in the title so I can see the date; keep that, but consider keeping the readable title beside it, for example "# Health Record — health-record-2026-10-24-0741", and say in the README which form it is so that a skill's reference files can match it.

5. **Where a cloud session keeps its working files.** The README has a job zip its working files beside its `State.md` in `In progress/`, for a workspace that may not last. A cloud session cannot write to the folder when it is attached as a copy, and its workspace is reclaimed when the session ends; the job pushed its files to a branch of my GitHub repository instead, with my leave. Say in the README that a session that can push to my repository may keep its working files there, named in `State.md`, and what it must never push (anything holding my personal data, the same rule as the folder's).

6. **Prompts that predate the stamping rule.** My prompt for the restructure, written for the 2026-10-24 version, asked for "a zip of a folder named health-record", while `release.py` has stamped names since the same day. Add a line to the README under *Outside this folder* that a prompt of mine naming a plain skill folder is satisfied by the stamped one, so a session does not stop to ask.

7. **The README's starting steps assume the desktop app.** Step 2 names the Mac path of the skills synced from claude.ai; a cloud session has no such folder and works from the copy I upload. Add the case: where no synced copy exists, the copy I give the session is the one to check against `About.md`'s md5s, and the first thing the session reports is whether it matches a recorded release.

8. **A changelog entry for a layout change.** The README caps an entry at a few lines, and `check_folder.py` notes one over 2,500 characters. A release that moves every section into files needs to say where each went; the job put that table in `About.md` (which is "current", so it should hold the map) and kept the changelog entry to what changed, why, and the md5s. Say in the README's table that the map of a multi-file skill lives in `About.md` and the changelog only names the release that introduced it.

9. **A third route in `Long skills/Method.md`: a structural change.** The method has two routes, a change I decided and an audit. A split or merge of files is neither: the rules do not change, the layout does, and what can break is reach — a rule out of the files a task opens, a pointer across a cut, a reason that rested on the old layout. The job ran it as: a measurement pass (section sizes; every positional pointer and where it lands) that chose the cut points; a build by script from the frozen original with a manifest of every move and every exact old/new rewrite; script checks (coverage, the reassembled diff, cross-references over all files, positional pointers per file, headers against headings, per-route load); then reader rounds. Write that route down in `Method.md`, in a paragraph of the same shape as the other two, pointing at the scripts from point 2.

10. **A lens the readers' briefs do not name.** Four readers walking tasks, forward and reversed, missed the one defect of substance the split created — a reason clause ("that comparison is free, both being in front of you") true only while the skill was one loaded text — and the reader given the changed-lines lens (every new or changed line, its parallels, and every reason near it that rests on "here", "above", "in front of you", "already", "free") found it. `Method.md`'s *Lenses* and *Where defects hide* should name reasons that rest on what is loaded or adjacent as their own class, and a structural change should always have one reader on that lens. Two readers reaching the same text was again a strong signal (three of round 1's findings came from both); a lens repeated on the fixed text by fresh readers found nothing, which is what the stopping rule asks for.

11. **The first-part measurement for any skill.** Claude Code keeps only the first 5,000 tokens of a `SKILL.md` after a compaction (its documentation, 2026-10-18). That matters for every skill whose main file is longer than that, split or not: whatever must always hold should sit in that first part, and the main file should say to reopen itself. Add the measurement (the character offset at which the always-needed part ends, against about 20,000) to the mechanical checks in `Process.md` — it names no path, so it can go there — and have `release.py` print it.

## What not to change

The one-text scripts are correct for one-text skills; the ask is a way to run them on several files, not a rewrite.
